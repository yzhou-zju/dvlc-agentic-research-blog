Improving heterogeneous robot collaboration: from D-VLC to GPT-guided research

Four robots coordinate perception and action across police and factory missions. Execution feedback informs the next software revision.

Foundation: D-VLC: Decentralized Vision-Language Collaboration for Heterogeneous Embodied Multi-Robot Systems in Unknown Environments.

01 / BACKGROUND

From collaboration to system improvement

Multi-robot teams can execute in parallel and combine complementary capabilities, yet these advantages do not automatically produce coordination. Conventional systems often encode rules for particular tasks such as exploration or mapping. A natural-language instruction instead states an outcome without specifying every action, resource assignment, or recovery step. In an unknown environment, robots must also share discoveries and turn a common goal into actions each platform can execute.

D-VLC: Decentralized Vision-Language Collaboration for Heterogeneous Embodied Multi-Robot Systems in Unknown Environments addressed this problem with decentralized, asynchronous perception, reasoning, and action. Capability-aware decomposition, compact spatial memory, and information exchange on demand support cooperation, while robot-specific modules execute unified decisions. Our two-floor task builds on that starting point and exposes waiting while carrying objects, repeated travel, and parallel assignments that delay completion.

The next step is to use these failures to improve the system used in the following run, rather than only replanning within the current run. Inspired by the feedback structure of recursive self-improvement (RSI), a GPT-6 Astra coding agent turns logs and test results into revisions of robot software and validation tools. Researchers define goals, constrain the changes, and judge the evidence. The robot system iterates; the model weights do not.

02 / EVOLUTION

From D-VLC to RSI-inspired, GPT-assisted system evolution

D-VLC showed heterogeneous robots exploring an unknown furnished home and a UAV requesting mobile-manipulator help at a door. The clips below show the home mission, the shared door-assistance view, and a separate close-up showing the door opening and a UAV flying through. The current four-robot framework extends this starting point to longer task chains, with GPT-6 Astra helping analyze, revise, and test the system.

Building on D-VLC’s on-demand cooperation, the current system adds a dependency-aware task program, four-robot concurrency, and failure recovery. The RSI-inspired research loop improves the robot system, not GPT weights. It begins with a specific run: which robot stopped, whether dependencies were satisfied, and how much time was spent on travel or model calls. GPT-6 Astra compares logs with code, proposes a testable cause, changes scheduling, perception, or recovery, and constructs replay, checkpoint, and full-task tests. A change is retained only when its benefit is attributable and it introduces no new blockage; otherwise it is narrowed or reverted. Experimental evidence and limits.

To reduce repeated pickup trips, for example, we tested moving an idle robot or object toward a future task. At one identical checkpoint, completion time fell from 422.1 to 352.1 seconds. A different early-positioning variant blocked another robot and was removed. Although a later full run finished, it did not trigger the predictive-pickup event, so that run cannot establish an end-to-end speedup from the strategy. A separate reference-image experiment raised false positives and recognition latency and was also left out. Retention and reversion make the improvement loop accountable to evidence.

03 / SYSTEM ARCHITECTURE

System architecture: online coordination and RSI-inspired software improvement

Two connected loops make up the architecture: robots adjust task execution from field feedback, while GPT-6 Astra uses experimental results to revise the next software version. The online execution loop derives a target catalog and dependency-aware task program from the mission, then grounds objects through field observations. In the latest factory and police runs, Qwen3.8 Flash Next handled online subtask decomposition, correction from action receipts, and evaluation of parallel options; Qwen3.5-4B handled action and exploration. The coordinator assigned work by dependencies, resources, and robot capabilities. GPT-6 Astra revised code and tests, but did not provide runtime subtask reasoning in these two runs. Archived films retain their actual model labels.

The objective of concurrency is shorter completion time, not the maximum number of busy robots. A robot waiting with an object may temporarily set it down and help elsewhere; early positioning helps only if it avoids blocking teammates and extra travel. The factory run shows repair and staging during discovery; the police run exercises a longer dependency chain. Read the factory mission and constraints

Explore the idle factory together, repair assembly machine M01, make a valve–pipe unit, and deliver it to D01 just inside the main gate. Finish by shutting down and disconnecting power. Identify seven target categories: M01, C01, D01, K01, one of E01/E02/E03, one of P01/P02/PIPE03/P04, and one of V01–V05. One usable item per alternative class is enough; the other locations are unknown.

M01 starts isolated with its repair hatch open, and power is disconnected. Install the whole K01 replacement kit in the repair slot; put a pipe and a valve into their respective staging fixtures. Repair and both staging branches may proceed during exploration without waiting for one another. Connect power and begin assembly only after all three are complete.

Pulling the output tray places the finished unit in the retriever’s hand; that robot delivers directly to D01 without another search or pickup. Then shut down at C01 and unplug the connector actually used. Robots assign work from capabilities and field feedback.

Read the police mission and constraints

Explore the police station together, repair the broken key cutter, make a batch of spare keys from the work order, inspect them, and deliver accepted keys to the handoff desk. Finish by shutting down and disconnecting power. Surface labels are ORDER, CUTTER, CONTROL, KEY, PERMIT, POWER, DELIVERY, and KEYS. Candidate repair modules are M-17/M-23/M-41 and blanks are B-AL/B-CU. The field diagnosis selects the module; the work order selects the blank. Their locations are unknown.

POWER starts disconnected, so there is no initial unplug step. Confirm isolation before repair; insert KEY, turn the lock, and open the service hatch. Replace the matching module, load the matching blank, then connect power. PERMIT can be brought to CONTROL and registered in parallel.

After the order is read, repair and blank loading are complete, power is connected, and the permit is registered, one robot must continuously hold the authorization button while another starts CUTTER. Release only after startup succeeds. Inspect the produced KEYS; take and deliver them only if they pass. After delivery, shut down at CONTROL and finally unplug POWER. Robots choose roles from capabilities and field feedback.

06 / RESEARCH METHOD

GPT-6 Astra as a research agent

In the earlier research workflow, researchers connected simulation observations, log analysis, failure hypotheses, code changes, and tests step by step. Here, researchers set mission goals, report field observations, and define change boundaries and acceptance criteria. A GPT-6 Astra coding agent relates events and timing to failures, proposes testable changes, revises the system and test tools, and checks them through replays, checkpoints, and full missions. Researchers still review the evidence and judge causal claims and side effects.

This forms an RSI-inspired research loop: run, diagnose, revise, validate, and run again. The object of improvement is the robot system and its test tools, not GPT-6 Astra’s model weights. Qwen3.8 Flash Next handled online subtask reasoning and correction in the latest factory and police runs. The available records show how this division of work operates, but cannot quantify human time saved; a passing local test also does not imply a faster full mission.
